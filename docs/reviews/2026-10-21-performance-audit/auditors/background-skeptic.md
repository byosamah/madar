# Skeptic report: background paths (key background)

Code read in /Users/osamakhalil/dev/madar/.claude/worktrees/deploy-test (main, 1d45aae5). No production contact. One docs fetch (Supabase Realtime limits page, read 2026-10-21).

New fact from the Supabase page "Realtime Limits" (Free plan): channel joins per second 100, messages per second 100, presence messages per second 20, and presence calls per client per 30 seconds 5. The last one matters for BG-1: a tab that flips its own state more than 5 times in 30 s hits the client limit. Madar's adapter then warns once and never tries again (presence.ts trackNow), while it already marked the state as tracked. Inferred from the docs. Not tested here.

## Verdicts

BG-1 weakened, score 4 to 3. The code is as described: deviceStateOf gives away at once when the page hides (activity.ts:17-20), and a test pins "away at once" as the owner rule (activity.test.ts:80). The cost model of proof.md (line 2150) used 150 computer changes a day, so the doubt is fair. But nobody measured the real flips, and a 15 to 20 s delay only removes the short hides. A long alt-tab to Revit still sends the same two frames. Production before the presence release used 15,878 of 2,000,000 messages (TASKS.md:931). The fix is a visible rule change (Away shows 15 to 20 s later), so it needs the owner. The docs limit of 5 presence calls in 30 s is a second reason to damp fast flips.

BG-2 weakened, score 5 to 3. The mechanism is real: each request starts a new worker and loads all office rows (officeCache.ts:96-133, server/CLAUDE.md). But the volume claim is too high. Production had 212 cold starts on 2026-10-16 (proof.md:968) and about 422 calls a day (chat presence design, "Cost"), not 5,000. At 60 to 120 KB that is 0.4 to 1.5 GB a month, not 18 GB. It grows with chats.typing (each typing call is a request with a cold load). The proposed fix is UNSAFE: the diff save writes the whole doc of a changed record (save.ts:15), and the User schema needs avatarUrl (entities.ts:224). A write that touches a user from a snapshot without the picture would erase the picture or fail the parse. A safe form must keep the picture in the write path: for example a slim copy only for read-only calls (userCard already drops picture data, views.ts:25), or a separate column. That is M to L work.

BG-3 confirmed, score 3. setResting leaves all status topics only after 30 minutes (activity.ts:12, presence.ts:197-205). A hidden tab for 5 to 30 minutes still receives every presence change. A rejoin costs about 15 presence_state frames, so a 5 minute threshold breaks even. The fix keeps the own topic tracked, so others still see Away. One small visible effect: after a return from 5 to 30 minutes, the dots of other people show Offline for a moment until the topics sync (the design rule "a topic that has not synced shows Offline"). The savings (0.2 to 0.4 million) are an estimate.

BG-4 weakened, score 3 to 2. realtime-js 2.117.2 has no visibility handling (grep) and a 25 s heartbeat (RealtimeClient.js:12). The Supabase docs describe the throttle. But nobody reproduced it, and the effect is bounded: others see Offline instead of Away for a tab hidden between 1 and 30 minutes, and a rejoin on show (the lists already reload after 60 s hidden, signals.ts:330). Step 1 (heartbeatCallback reconnect) is safe. Step 2 (worker true) needs a worker file and a CSP change (worker-src 'self', headers.template:19): that is a security rule, so ask the owner. Do step 1 alone first.

BG-5 confirmed, score 3. affects() reloads every read with scope 'person' whose kinds hold messages, with no conversation check (signals.ts:75-87, readMap.ts:93-95). 'messages' is not a personal kind (readMap.ts:30). So every message of the office reloads chats.messages (200 messages) and chats.list in each visible tab that shows them. The fix as written is UNSAFE: a read of only the newer messages would miss reactions, edits, deletes and Seen changes on the 200 messages already held, and chats.messages has no 'after' input (handlers/chats.ts:291-300, only 'before' and 'around'). Safe forms: name the chat in the person signal for its members (the anonymous office signal must stay anonymous, INT-16), so other open chats skip the reload; or leave as is. Effort L.

BG-6 weakened, score 3 to 2. Sizes are right (maplibre 282 KB, worker 145 KB, rtl 44 KB, css 10 KB gzip, measured on the baseline dist). One claim is wrong: the map does not load in parallel with the project data. ProjectPlace needs the loaded detail (ProjectPlace.tsx:14), so the load starts after the project answer. The files are content hashed and cached for a year, so the cost is the first visit of a pinned project on a device, and again only when the dependency changes. Fix (load at idle or near view, keep the grey box) is safe.

BG-7 weakened, score 3 to 2. FileRow asks the link for each picture at mount (FilesTab.tsx:38), true. But the img is loading=lazy (line 63), so only rows within about 1,250 px load bytes. For 60 pictures that is roughly 25 to 30 files, about 3 MB, not 4 to 8 MB. The link calls (5 batches) are real. Gate with the near-view hook: safe.

BG-8 weakened, score 2 to 1. True, but small: production made about 13,000 calls a month (design), so 1,200 to 3,000 more is under 1 percent of the free 500,000. The fix as written is not safe: a 24 hour skip delays the repair when the server deleted the device (a 404 or 410 push answer, push CLAUDE.md "The path" step 4, or the keys repair). Recommend no change.

BG-9 weakened, score 2 to 1. Mechanism confirmed (typing.ts:121-165, calls/typing.ts). The count (about 240 calls a day) is small against 500,000 a month. Skipping the stop call is not free: the board removes a typist only on a stop signal or after 8 s (typing.ts:48-57, TYPING_SHOW_MS), so the line would stay up to 8 s after a send unless a new receiver rule drops it on the new message (about 1 s later). That is a small visible change. Not worth it for one call in four.

BG-10 weakened, score 2. Code confirmed (triggers.ts:42-65). Two corrections. First, the proposed read-only first pass cuts the lock time only. It still reads the same rows, so it does not cut the egress the finding claims. Second, the lock window is a few hundred ms every 15 minutes, so a user save almost never waits. A real saving is in loadJobs: the reminders need only tasks with a due date (notify.ts:197 skips tasks with none), so add a SQL filter on the due date (not null) and pick only the fields the trigger reads. Egress at year size (about 0.3 MB of tasks plus the office, 96 runs a day) is about 1 GB a month by estimate, but today's office is far smaller.

BG-11 weakened, score 2 to 1. The second reload happens only when the socket died while the tab was hidden or asleep. In the normal case one reload runs (signals.ts:326-335). invalidateQueries cancels an in-flight refetch by default, so the two passes often merge. The second pass is needed: signals can be lost until the rejoin. Skipping it risks a lost change. Leave as is.

BG-12 weakened, score 2. True that each files.link signs a new token (supabaseStorage.ts:107-114) and the URL changes after 8 minutes (files.ts:19). The cost is one re-download of the visible pictures on a return after 8 minutes. The proposed service worker cache stores private pictures on the device. That changes the security surface (a shared browser, a sign-out) and needs the owner. Not a safe change by itself.

BG-13 confirmed, score 1. thumbKey is null for report screenshots (feedback.ts:42) and the list loads the original (FeedbackSection.tsx:41, lazy only). It is still open in TASKS.md:254. Admin only, a few times a week.

BG-14 weakened, score 1. The write per key press is real (drafts.ts:70-76) but costs well under 1 ms for chat text. The delayed write has a risk: a late write after sign-out could bring back a draft that keepDraftsOf just removed. Not worth it.

BG-15 confirmed, score 1. The limit is 100 joins a second on Free (docs page, verified). A burst of 255 joins needs all 15 tabs to join in the same second: it happens at a Realtime restart, not at a normal release (each tab reloads when its next call gets client_outdated). Random jitter on REJOIN_MS is safe. Grouping the joins adds a small delay to the first status dots.

BG-16 confirmed, score 2. chatLine runs session.get and chats.list as each recipient (line.ts:100-117). The pushes of one save run one after the other. It runs after the answer, so no screen waits. Small egress. Parallel runs are safe with a cap of 3 or 4 (pooler clients, see the EMAXCONN note in server/CLAUDE.md). A narrow single-chat read needs a new loader and shadow tests (medium).
